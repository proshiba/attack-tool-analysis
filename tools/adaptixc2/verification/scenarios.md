# AdaptixC2 verification scenarios

## Scope

- **VM 100 — Kali — `192.168.1.50` — only C2, staging, build, and operator host.** The AdaptixC2 source, dependencies, server, extenders, generated agents, listener state, HTTP staging service, and operator API calls remain on this VM. The teamserver and every Beacon listener bind to this address or loopback.
- **VM 104 — Windows — historical target only.** The completed v1.2 Windows verification below used `192.168.1.52` and `win_verify_baseline`; VM 104 is not touched by the Linux expansion.
- **VM 103 — Ubuntu — `192.168.1.51` — Linux target for this expansion.** It begins and ends at `linux_verify_baseline`. It may fetch one reviewed generated Linux ELF and one fixed marker only from VM 100, connect only to the VM 100 listener, and send DNS only to VM 100 while the resolver and IPv4/IPv6 guards are in force.
- **VM 105 — REMnux — static-analysis host only.** It may receive generated binaries out of band for `file`, PE metadata, strings, and disassembly review. It never executes an AdaptixC2 component and is not a payload or C2 destination.
- **VM 106 — NSM — offline packet-analysis host.** `nsm-analyze` receives saved pcaps out of band. Any active JARM probe is permitted to address only the listener on `192.168.1.50`.
- **Destinations.** Every delivery, server probe, agent callback, operator action, and active fingerprint destination is `192.168.1.50`, `192.168.1.51`, `192.168.1.52`, or loopback. Public threat-intelligence indicators supplied with the task are citations only: they are neither resolved nor copied into a profile. No attack traffic may target a public host, the management network, VM 102, VM 108, VM 109, or VM 110.
- **Bounded actions.** Agent tasking is limited to identity, working-directory, process, and directory survey plus download of one fixed small marker created for the run. The Linux persistence flow installs exactly one lab-scoped `sysmon.service` unit whose `ExecStart` is the reviewed renamed agent, then captures creation, enablement, and start before rollback. The DNS preflight changes only the target resolver and temporary egress rules and restores neither by hand because rollback is authoritative. No credential access, privilege escalation beyond the root context required for the unit, process injection, lateral movement, tunneling, self-propagation, destructive action, or unrelated-file collection is allowed.

## Grounding and scenario selection

[Censys, “AdaptixC2: fingerprinting an open-source C2 framework at scale”](https://censys.com/blog/adaptixc2-open-source-c2-framework/) reports that the default response headers and default 404 body identify exposed AdaptixC2 infrastructure, and specifically claims the body remains useful when operators change headers. This verification treats that as a falsifiable claim: capture the default response from the target and pcap, modify only the response headers, repeat the probe, and run the same body rule against both flows.

[Group-IB, “JadeProx: Tracing a China-nexus Operation Through an OPSEC Mistake”](https://www.group-ib.com/blog/jadeprox-china-nexus-triback-loader/) documents signed-host DLL sideloading, rotating Win32 callback APIs, and AdaptixC2 delivery. [Seqrite, “Operation Dragon Weave”](https://www.seqrite.com/blog/operation-dragon-weave-uncovering-a-china-linked-campaign-targeting-czech-republic-and-taiwan-using-azure-cloud-c2/) documents ZIP/LNK or Rust-loader delivery converging on a signed executable loading `UnityPlayer.dll`, followed by an Adaptix-derived AZUREVEIL agent. The lab reproduces only the bounded detection surface: a signed binary already on VM 104 loads a lab-authored inert DLL from its application directory. It does not reproduce shellcode, callback-API execution, decryption, lures, or the reported malware.

[JFrog Security Research, “Shai-Hulud: Here We Go Again — Worm by TeamPCP Hits NPM and PyPI”](https://research.jfrog.com/post/shai-hulud-here-we-go-again/) documents TeamPCP use of AI-API-looking paths such as `/v1/models` and `/v1/weights`. The task’s reported AdaptixC2 infrastructure pivot used an HTTP header fingerprint. Those paths are useful examples of operator customization, not defaults, and are not converted into an AdaptixC2-only signature without observed invariant evidence.

### Linux platform reality at v1.2

The requested Linux HTTP/S Beacon and Linux DNS/DoH Beacon cannot be generated by the reviewed upstream tree. AdaptixC2 v1.2 and current `main` are the same commit, `a4b80bf370f704d6843e69433bfb5c06274f57df`. Its `beacon_agent` builder selects `x86_64-w64-mingw32-g++` or `i686-w64-mingw32-g++`, links Windows objects, and emits only Windows PE formats. Its separate `gopher_agent` builder emits Linux ELF, but `GenerateProfiles` accepts only the Gopher TCP/mTLS listener protocol. The Censys payload table corroborates the source: the observed Linux `timesync.bin` is identified as a Gopher agent, while all listed Beacon payloads are Windows executables.

This distinction is detection-relevant and is not papered over. The Linux run uses the genuine generated Gopher ELF over mTLS, and records that its transport is a continuous connection with reconnect delay rather than Beacon sleep/jitter. The DNS flow stops after lab resolver/listener guard validation unless a genuine Linux-capable Adaptix DNS agent can be produced from the reviewed source; no Windows Beacon is run on VM 103 and no lab-authored traffic generator is represented as agent evidence.

## Deferred and lab-capability gaps

- **Azure Blob dead-drop — lab-capability gap.** The reported AZUREVEIL channel requires a public cloud endpoint. Absolute safety Rule 1 forbids resolving or contacting it, so it can never be executed in this lab topology.
- **macOS agent — lab-capability gap.** The lab has no macOS target.
- **SMB and TCP pivoting — future bounded scenario.** They require a separate scope design and add no evidence needed for the requested HTTP/S and sideload verification.
- **Linux Beacon HTTP/S and DNS/DoH — upstream platform gap.** The v1.2/current source cannot generate those combinations. The official Linux agent is Gopher and accepts TCP/mTLS only. This is distinct from a lab-capability gap: changing the lab cannot add a transport the reviewed upstream builder rejects.
- **DoH endpoint — lab-capability gap.** The source defaults name public resolvers. The lab has no hosted DoH endpoint compatible with this agent, and public endpoints are categorically forbidden, so DoH is not run.
